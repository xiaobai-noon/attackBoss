# 《打boss》对话与场景系统设计

> **文档版本**：v1.0
> **状态**：设计稿 + 垂直切片原型已交付
> **关联文档**：[`职级轮回_游戏策划书.md`](./职级轮回_游戏策划书.md)（v1.1）、[`UI设计方案.md`](./UI设计方案.md)（v1.0）
> **本文解决**：把游戏从「数值表格 + 文字选项」升级为「**场景 + 对话 + 分支**」的表现形态（对标杆：《完蛋，我被美女包围了》的交互模式）。
> **纪律**：本文不推翻策划书的数值/结局/事件规则。**数值层完全复用 `GameState` / `EventBus`，只替换表现层与事件承载形式。**

---

## 0. 先算清账：为什么不能照抄《完蛋》

《完蛋，我被美女包围了》是 **FMV（全动态影像）游戏**：真人实拍，全片约两千余个视频片段，每个选项对应一段独立影像。它的成本结构是「**拍摄预算 × 分支数量**」。

**核心矛盾：选项分支会让视频片段数量指数膨胀。**

```
3 个选项 × 20 个事件 × 每年重玩 = 天文数字
```

真人实拍你走不了；但你有 `E:\AiVideo\ai-shortdrama` —— 里面已经跑通了
**即梦/快手图像 → MiniMax TTS → 可灵 Avatar 数字人对口型 → FFmpeg 合成** 这条链路。
这意味着你可以做「**AI 生成影像的 FMV**」，但**仍然必须做分级表现**，否则 API 调用量同样会爆炸。

**结论：只有情绪转折点才上视频，日常对话用立绘 + 打字机。**

## 1. 三层表现（本系统的地基）

| 层 | 承载形式 | 覆盖镜头占比 | 生产手段 | 复用成本 |
|---|---|---|---|---|
| **A. 场景底** | AI 生成静态场景图 + 呼吸式运镜（Ken Burns） | 100% | 即梦 / 快手图像，每场景 1 张 | 极低（一张图用几十次） |
| **B. 角色立绘** | AI 生成角色 + 表情差分（3~5 张/人） | 约 90% | 首张定妆图 → 图生图做差分（锁 seed + reference） | 低 |
| **C. 动态说话** | 可灵 Avatar 对口型短视频（3~6 秒） | 约 8% | `avatar_kling.py` 已有链路 | **高（按次计费）** |
| **D. 结局影像** | B-roll 拼剪 + 字幕 + 旁白 | 5 个结局 | FFmpeg 合成 | 中（一次成型） |

**C 层的准入条件（写进剧本审查规则，防止滥用）**：
只有当台词同时满足「**立场反转 / 情绪爆发 / 结局独白**」三者之一，才标记 `clip` 走视频。其余一律立绘。

> 资产量级估算（首年内容）：
> 场景 10~12 张 · 立绘 5 人 × 4 表情 = 20 张 · 视频片段控制在 **30~60 段** · 主角不露脸（第一人称视角，省掉全套主角资产）。

## 2. 对话图（Dialogue Graph）—— 核心数据结构

现有 `data/events.json` 的结构是「事件 → 3 选项 → 效果」，**承载不了对话**。升级为**节点图**。

### 2.1 节点类型

| `type` | 作用 | 必需字段 |
|---|---|---|
| `bg` | 切换场景 / 时段（驱动背景图与光照） | `scene`、`slot`、`next` |
| `line` | 一句台词 | `speaker`、`text`、`next`；可选 `emotion` / `side` / `clip` |
| `choice` | 玩家选项 | `options[]`（每项含 `text`、`goto`） |
| `effect` | 纯数值结算（不产生画面） | `deltas` / `npc_effects` / `flags_add`、`next` |
| `branch` | 条件跳转 | `conditions[]`（含 `if` 与 `goto`）、`default` |
| `goto` | 无条件跳转 | `goto` |
| `end` | 剧本结束 | 可选 `ending` |

### 2.2 `speaker` 取值约定

- NPC：`shen_tinglan` / `ji_heng` / `you_wanxing` / `tang_poxiao` / `liang_xu`
- `player`：玩家（第一人称，名字牌显示「你」）
- `narrator`：旁白（无名字牌，立绘压暗）

### 2.3 条件表达式（`branch.conditions` / `option.show_if`）

```json
{ "stat": "mind_load", "op": ">=", "value": 70, "goto": "n41" }
{ "flag": "reform_seed", "goto": "nX" }
{ "favor": "shen_tinglan", "op": ">=", "value": 60, "goto": "nY" }
```
多个键写在同一个 condition 对象里 = **逻辑与**。`op` 支持 `>= > <= < == !=`。

### 2.4 完整示例（节选）

```json
{
  "id": "evt_01_weekly_report",
  "title": "周报扩写运动",
  "scene": "meeting_room",
  "slot": "morning",
  "entry": "n1",
  "nodes": {
    "n1": { "type": "bg", "scene": "meeting_room", "slot": "morning", "next": "n2" },
    "n2": { "type": "line", "speaker": "narrator", "text": "周一上午九点，部门周会。", "next": "n3" },
    "n3": { "type": "line", "speaker": "ji_heng", "emotion": "smug", "side": "left",
            "text": "「周报从这周起升级——三句话不够，要一页纸。」", "next": "n4" },
    "n4": { "type": "choice", "prompt": "你怎么回？", "options": [
        { "text": "堆砌漂亮空话交差", "goto": "n10" },
        { "text": "只写可验证事实与风险", "goto": "n20" },
        { "text": "联合几人提议恢复短周报", "goto": "n30" }
    ]},
    "n10": { "type": "effect", "deltas": { "performance": 4, "expertise": -1 },
             "npc_effects": {}, "flags_add": [], "next": "n11" }
  }
}
```

**与旧 `events.json` 的关系**：`events.json` 保留为「**索引 + 抽取条件**」（`id / weight / min_rank / tags`），
增加 `story` 字段指向 `data/story/*.json`。抽到事件后，加载对应剧本进 `DialogueEngine` 播放。
**加权抽取逻辑（`event_loader.gd::pick_weighted`）完全不动。**

## 3. 日循环（"每日随机时间"的落地方式）

策划书 §3.1 的 `year / quarter / week` 骨架**保留**，把 `week` 向下展开：

```
年 (year)
 └ 季 (quarter, 4)
    └ 周 (week, 3)            ← 策划书现有粒度，年末晋升判定不变
       └ 工作日 (day, 5)      ← 新增：周一 ~ 周五
          └ 时段 (slot, 3)    ← 新增：上午 / 下午 / 加班
```

**触发规则（关键：控制事件密度）**

| 规则 | 值 | 理由 |
|---|---|---|
| 每天最多触发事件数 | 1 | 避免节奏失控 |
| 事件日触发概率 | 约 40% | 一年 12 周 × 5 天 = 60 天，约产出 24 个事件/年，与 20 事件池 + 12 周骨架吻合 |
| 未触发事件的时段 | 播放**环境描写**（1~2 条旁白，自动推进，点一下跳过） | 让"上班"有实感，而不是空转 |
| 无 `clip` 标记的立绘、`slot` 决定光照 | `morning` 冷白 / `afternoon` 暖白 / `overtime` 低照度 + 噪点 | 零成本时段辨识 |

**事件池按时段过滤**：`bg` 节点的 `slot` 同时作为可用性约束——
「无效对齐会」只能出现在 `morning`/`afternoon`，「深夜办公室」类事件只在 `overtime`。

**存档新增字段**：`day`（1~5）、`slot`、`story_id`（未完成剧本的中断续播点）。
> ⚠️ 需同步 `SAVE_SCHEMA_VERSION` 升到 3，并在 `load_game()` 里做旧档拒绝（沿用现有做法）。

## 4. Godot 落地：节点结构与文件

```
DialogueScreen (Control)
├─ Bg                  ColorRect              ← A 层：场景底（后期换 TextureRect + 呼吸运镜）
├─ SceneName           Label                  ← 占位水印，接美术后删除
├─ PortraitLeft        PanelContainer         ← B 层：立绘位（左）
├─ PortraitRight       PanelContainer         ← B 层：立绘位（右）
├─ TopBar              HBoxContainer          ← 年/季/周/日/时段 + 七维精简
└─ Bottom              VBoxContainer
   ├─ ChoicesBox       VBoxContainer          ← 动态生成选项按钮
   ├─ SpeakerWrap      PanelContainer          ← 名字牌
   └─ DialoguePanel    PanelContainer
      └─ DialogueText  RichTextLabel          ← 打字机（visible_characters 递增）
```

**文件落点**

| 文件 | 职责 |
|---|---|
| `scripts/dialogue_engine.gd` | **对话图执行器（VM）**。纯逻辑，不引用 `GameState`，通过 Callable 适配器访问状态 → 可 headless 测试 |
| `scenes/dialogue_screen.tscn` / `.gd` | AVG 表现层：渲染场景/立绘/对话/选项，转发玩家输入 |
| `data/story/*.json` | 剧本节点图 |
| `data/events.json` | 保持为事件索引，增加 `story` 字段 |
| `scenes/year_hub.tscn`（原 `day_screen`） | 保留为年度总览 + 「开始今天」入口 |

**分层原则**：`DialogueEngine` 不认识任何 UI 节点；`DialogueScreen` 不做任何数值计算。
这是上次 `UI设计方案.md` §8 提到的「结算逻辑从 UI 剥离」的具体落地。

## 6. 资产生产管线（复用 ai-shortdrama）

```
1. 剧本节点图（人工写 JSON）
      ↓ 导出「分镜表」：每行 = {node_id, speaker, emotion, scene, slot, 是否需要 clip}
2. 场景图：ImageProvider（即梦/快手）批量生成 → assets/bg/{scene_id}.png
3. 立绘：每个 NPC 先生成定妆图（锁 seed）→ 图生图出表情差分
      → assets/sprite/{npc_id}/{npc_id}_{emotion}.png
4. 关键台词视频：TTSProvider 合成该句音频 → AvatarProvider 出对口型视频
      → assets/clip/{story_id}_{node_id}.mp4
5. 校验：缺图的 node 自动回退到占位色块（原型已实现此回退）
```

**命名规范（必须固定，否则后期无法批量替换）**

```
res://assets/bg/{scene_id}.png
res://assets/sprite/{npc_id}/{npc_id}_{emotion}.png
res://assets/clip/{story_id}_{node_id}.mp4
res://assets/audio/bgm/{slot}.ogg
```

**一致性风险**：AI 生图最大问题是同一个 NPC 跨图脸不一致。
对策：① 定妆图锁 seed；② 以定妆图作 reference image 走图生图；③ 立绘构图固定（半身、正面偏 15°），降低一致性的可见度。

## 8. 待决策（阻塞项）

1. **视觉形式**：立绘为主 / 视频为主 / 分层混合（本文推荐分层混合）。
2. **主角是否露脸**：第一人称（省一整套主角资产）vs 第三人称（需要主角立绘 + 表情）。
3. **日循环密度**：40% 触发率是否合适（直接决定剧本产量压力）。
4. **本系统的模块编号**：是否新增 M9「对话系统」，或作为 M3 的替换实现。
